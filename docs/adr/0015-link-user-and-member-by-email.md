# 0015. ログインユーザーとメンバーをメールアドレスで結び付ける

- **Status**: Accepted
- **Date**: 2026-11-04
- **Deciders**: tommykey0925

## Context

部署で絞り込むプルダウン (タイムライン・割り当て一覧・メンバー一覧) の初期値を、ログインユーザーの部署にしたい。

ログインユーザー (Auth.js の User) と、画面に表示するメンバー (Resource) は同じ人を指す。
しかし今は別々に管理していて、両者をつなぐ属性がない。
部署 (`departmentId`) は Resource だけが持ち、User は持たない。

## Decision

Resource にメールアドレス (`email`) を必須の属性として足し、ログインユーザーのメールアドレスと照合して結び付ける。

- 部署は Resource だけに持ち続ける。User には複製しない
- メールアドレスはチーム内で一意にする。作成・更新の前にチームのメンバーを読んで重複を確認する
- 保存時に前後の空白を除き、小文字にする。Auth.js はログイン時に同じ正規化をする (`@auth/core` の `lib/actions/signin/send-token.js` にある `defaultNormalizer`)
- ログインしないメンバー (パートナー会社の要員など) には、届かないことが保証された仮のアドレス (`*@example.invalid`、RFC 2606) を入れる
- 部署プルダウン (タイムライン・アサイン一覧・メンバー一覧) は、URL に部署の指定がないとき、照合したメンバーの部署を初期値にする。未所属なら「未所属」、照合できなければ「すべての部署」
- URL にキーがない状態は「初期値」を意味するので、「すべての部署」は `__all__` という値を URL に書いて表す (既存の未所属 `__unassigned__` と同じ形)

## Consequences

### Positive

- 部署の情報が Resource の1か所に保たれ、ずれが起きない
- メンバー登録の時点で照合キーが決まる。初回ログインを待たずに結び付けられる
- 必須にしたので、社員のアドレスの入れ忘れで絞り込みが黙って効かなくなる事態を、登録の時点で防げる

### Negative

- 重複の確認は「読んでから書く」なので、同時に2人が同じアドレスで登録する競合は防げない。部署名の重複確認 (ADR 0013) と同じ割り切り
- ログインしないメンバーにも仮のアドレスを考えて入れる手間がかかる
- メンバーのアドレスを変えると、その人のログインとの結び付きも変わる

### Neutral

- 既存の9人には、本機能の実装前に仮のアドレスを一括で入れた (2026-11-03、git 管理外の1回限りのスクリプト)
- 読み込み時に `email` 属性がない行は空文字として扱う

## Alternatives considered

- **User に `departmentId` を持たせる**: 部署の情報が2か所に分かれ、どちらが正しいか決まらなくなる
- **Resource に `userId` を持たせる**: User は初回ログインまで作られないので、メンバー登録の時点で値を決められない
- **メールアドレスを任意にする**: 社員のアドレスを入れ忘れても気づけず、その人の画面では絞り込みが適用されない
- **一意性を専用の項目 (`RES_EMAIL#{email}`) とトランザクションで保証する**: 競合は防げるが、作成・更新・削除・一括削除のすべてで項目の付け外しが必要になる。チームの規模では競合の起きる見込みが小さい
